1//! Read FoundationDB client transaction profiling data.
2//!
3//! When client profiling is enabled (`fdbcli> profile client set <rate> <size limit>`),
4//! every FoundationDB client samples transactions at the given rate and records their
5//! operations (read version, gets, range reads, commits and their errors). Every
6//! `CSI_STATUS_DELAY` (10 seconds by default) the client flushes the recorded
7//! transactions into the system keyspace under [`PROFILE_PREFIX`]
8//! (`\xff\x02/fdbClientInfo/client_latency/`), split in chunks keyed by versionstamp and
9//! transaction id. See the [transaction profiler documentation].
10//!
11//! This crate turns that keyspace into typed [`Event`]s. It does no I/O and depends on no
12//! version of the FoundationDB bindings: the application reads the rows with its own
13//! client, in its own transaction and retry loop, and hands them to
14//! [`ProfileScanner::read_page`], which reassembles and decodes the chunks of one page,
15//! decides where the page stops, and returns a resumable [`Cursor`]. Only records
16//! written by 7.1+ clients are decoded (see [`decode_events`]).
17//!
18//! # Example
19//!
20//! With the `foundationdb` crate:
21//!
22//! ```no_run
23//! use foundationdb::options::TransactionOption;
24//! use foundationdb::{ClientBudget, Database, FdbBindingError, KeySelector, RangeOption};
25//! use foundationdb_profiling::{Cursor, Page, ProfileScanner};
26//! use futures_util::TryStreamExt;
27//! use std::time::Duration;
28//!
29//! # async fn example(db: &Database) -> Result<(), FdbBindingError> {
30//! let scanner = ProfileScanner::new();
31//! let cursor = Cursor::beginning();
32//! let page: Page = db
33//!     .run(|trx, _| {
34//!         let scanner = scanner.clone();
35//!         let cursor = cursor.clone();
36//!         async move {
37//!             // Options are the caller's job: this crate never sets any.
38//!             trx.set_option(TransactionOption::ReadSystemKeys)?;
39//!             // Bound every page, well under the 5 second transaction lifetime.
40//!             trx.set_client_budget(ClientBudget {
41//!                 time_limit: Some(Duration::from_secs(2)),
42//!                 ..ClientBudget::default()
43//!             });
44//!             let range = scanner.range(&cursor);
45//!             let opt = RangeOption::from((
46//!                 KeySelector::first_greater_or_equal(range.begin.as_slice()),
47//!                 KeySelector::first_greater_or_equal(range.end.as_slice()),
48//!             ));
49//!             let rows = trx
50//!                 .get_ranges_keyvalues(opt, true)
51//!                 .map_ok(|kv| (kv.key().to_vec(), kv.value().to_vec()));
52//!             let page = scanner
53//!                 .read_page(&cursor, rows, || trx.check_client_budget().is_err())
54//!                 .await
55//!                 // FoundationDB errors go back to the retry loop, other errors are
56//!                 // boxed as a custom error.
57//!                 .map_err(|err| err.into_error(FdbBindingError::new_custom_error))?;
58//!             Ok::<_, FdbBindingError>(page)
59//!         }
60//!     })
61//!     .await?;
62//! for tx in &page.transactions {
63//!     println!("{} {:?}: {} events", tx.version, tx.id, tx.events.len());
64//! }
65//! // Persist `page.next.as_bytes()` to resume from there later.
66//! # Ok(())
67//! # }
68//! ```
69//!
70//! See `examples/top_keys.rs` for a runnable end-to-end example that pages through the
71//! whole keyspace and prints the hottest keys, ranges and write hot spots.
72//!
73//! # The caller's contract
74//!
75//! For each page, the caller reads exactly [`ProfileScanner::range`] of the page's
76//! cursor: forward, with snapshot reads and no row limit, both ends as
77//! `first_greater_or_equal` key selectors, and gives [`ProfileScanner::read_page`] the
78//! rows as a [`Stream`](futures_core::Stream) of `Result<(key, value), E>`. A row
79//! outside that range or out of key order fails the page with
80//! [`ScanError::InvalidRows`], and a stream error comes back as [`ScanError::Source`] so
81//! the caller can hand it to its retry loop.
82//!
83//! On that transaction:
84//!
85//! - `TransactionOption::ReadSystemKeys` (or its equivalent) is required, the data lives
86//!   in the system keyspace.
87//! - `TransactionOption::ReadLockAware` is required if the cluster may be locked (for
88//!   instance a DR secondary).
89//!
90//! # Bounding a page: the stop check
91//!
92//! The `should_stop` closure given to [`ProfileScanner::read_page`] is required, and is
93//! the only place where the caller bounds a page: a transaction budget as above, a row
94//! count, anything. [`ProfileScanner::read_page`] calls it after every row and stops as
95//! soon as it returns `true`; otherwise the page reads to the end of its range. Without
96//! a real bound, a large range can outlive the transaction and hit
97//! `transaction_too_old`. Base the check on a caller-pluggable clock rather than the
98//! wall clock when the code must be reproducible, for instance under simulation.
99//!
100//! # Paging and tailing
101//!
102//! [`Page::next`] is always a valid place to resume from, and [`Page::exhausted`] tells
103//! whether the page reached the end of its range (`false` when the stop check stopped
104//! it). To read a range in several transactions, loop on [`ProfileScanner::read_page`]
105//! with `cursor = page.next` until [`Page::exhausted`]: every transaction is returned
106//! once over the sequence of pages, even when the client wrote its chunks in two commits
107//! with other records in between, and even when a page stops between them: the next
108//! page resumes at the first chunk of the oldest incomplete record. A record is lost
109//! (reported as [`SkipReason::BrokenChunks`]) only when the stop check does not let a
110//! single page read from its cursor to the end of the records that overlap it (in
111//! practice, a single record cannot be read from the cursor before the caller says
112//! stop): the records still incomplete at that stop are broken, and the page still
113//! advances.
114//!
115//! To tail the keyspace, persist `page.next` ([`Cursor::as_bytes`] /
116//! [`Cursor::from_bytes`]) and keep polling from it: an exhausted page's cursor picks up
117//! the records flushed after it, including the second half of a record split across two
118//! commits. [`Cursor::at_version`] starts at a commit version, and
119//! [`ProfileScanner::end_version`] bounds a page by one. A transaction whose chunks
120//! straddle `end_version` is not returned by that bounded read, the cursor stays on its
121//! first chunk.
122//!
123//! Note that the version of a record is the one at which the client flushed it, some time
124//! after the profiled transaction ran.
125//!
126//! # When profiling data is flushed
127//!
128//! The C++ client records a sampled transaction's events when its native transaction is
129//! destroyed. With the `foundationdb` Rust bindings, that happens when the `Transaction`
130//! (or the `RetryableTransaction` of a `Database::run` closure) is dropped. In particular a
131//! `TransactionCommitError` owns the transaction and keeps it alive until the error is
132//! dropped (or recovered with `on_error`), so holding on to such errors delays the
133//! profiling data of the failed transaction. The data then reaches the keyspace at the
134//! client's next flush, up to `CSI_STATUS_DELAY` later.
135//!
136//! # Aggregation
137//!
138//! [`Aggregator`] counts the keys and ranges read and written by the transactions of one
139//! or more pages, like the Python `transaction_profiling_analyzer`.
140//!
141//! [transaction profiler documentation]: https://apple.github.io/foundationdb/transaction-profiler-analyzer.html
